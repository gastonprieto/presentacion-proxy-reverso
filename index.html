Enrutamiento

Reglas: ruta → servicio

/usuarios/ordenes/pagos/static

El proxy tiene una tabla de reglas. La primera que coincide con la ruta decide el servicio. Cambiala en vivo.

Reglas del proxy
  • Sin regla para una ruta: 404 desde el proxy.
  • Regla hacia el servicio equivocado: el pedido llega, pero el servicio no conoce la ruta y el 404 lo da él.
  • También se puede enrutar por host (api. vs. www.) o por header (X-Version: 2).
Mostrar la tabla: cada fila es "si la ruta empieza con…, mandala a…". Tocar "＋ Pagos v2" y elegirlo en la fila de /pagos: los pedidos verde agua empiezan a ir al servicio nuevo. Así se hace una migración sin que el cliente cambie nada. Elegir "— sin regla —" en alguna fila para ver los 404: salen del proxy, el pedido no llega a ningún servicio. Después apuntar una fila a un servicio que no corresponde (por ejemplo /usuarios → Pagos): el pedido viaja hasta Pagos y el 404 aparece sobre Pagos. El proxy no sabe qué rutas entiende cada servicio; solo sigue la regla. Pregunta para la clase: ¿cómo usarían esto para probar una versión nueva con solo una parte del tráfico?
Una sola puerta

El cliente conoce una sola dirección

el cliente siempre le habla a tienda.com

Atrás puede haber uno, cuatro o veinte servicios. El cliente no lo sabe: solo conoce al proxy.

Reglas del proxy
  • Partir un servicio en dos es agregar una regla: el cliente no cambió nada.
  • Los servicios no quedan expuestos a internet: solo el proxy.
Al principio, /ordenes/envios lo atiende Órdenes (la regla /ordenes coincide por prefijo). Tocar "Separar Envíos": aparece un servicio nuevo y una regla más específica antes de /ordenes. Los pedidos verde lima van ahora a Envíos y los clientes siguen pegándole a tienda.com. Pregunta para la clase: sin proxy, ¿qué tendría que cambiar en la app móvil para hablar con un servicio nuevo?
En la puerta

Lo que se resuelve una sola vez, adelante

/usuarios/ordenes/pagos/staticcachérespuestacifrado

Como todo pasa por el proxy, hay tareas que conviene hacer ahí y no repetirlas en cada servicio.

Prender la caché: los pedidos blancos (/static) se responden en rosa desde el proxy y la barra de Web deja de crecer. Es carga que el servicio no ve. Prender TLS: los links de los clientes se ponen verdes y los puntos de ese tramo llevan un anillo blanco (van cifrados). Del proxy a los servicios no hay anillo: el TLS termina en el proxy y adentro es HTTP. Antes de prenderlo, la etiqueta dice "texto plano". Prender compresión: las respuestas que salen del proxy hacia los clientes se achican y baja el número de KB/s. Los servicios no se enteran. Las tres son el mismo argumento: hacerlo una vez en la puerta, no en cada servicio. Pregunta para la clase: ¿qué otras cosas tendría sentido resolver en la puerta para todos los servicios?
Proxy + LB

Primero la ruta, después la carga

cada cajita es una réplica, con los pedidos que atendió

El proxy elige el servicio por la ruta. Adentro de cada servicio hay varias copias, y entre ellas se balancea como en la clase anterior.

  • Muchos proxies hacen las dos cosas: enrutan y balancean.
  • Cada servicio escala por separado, según su propia carga.
Mostrar que cada servicio tiene sus réplicas y que el reparto entre ellas es parejo (round robin). Sumar réplicas de Órdenes: el proxy las incorpora y reparte entre todas. Pregunta para la clase: si Órdenes recibe diez veces más tráfico que Usuarios, ¿cuántas réplicas le darían a cada uno?
Riesgos

Si se cae la puerta, se cae todo

👆 clic en un proxy para apagarlo

Todo el tráfico pasa por el proxy: es un punto único de falla.

  • Se mitiga con un esquema activo/pasivo: la pasiva queda en espera y toma el tráfico si la activa se cae (failover).
  • Suma un salto más de latencia a cada pedido.
  • Tentación peligrosa: meter lógica de negocio en el proxy.
Clic en el proxy: todos los pedidos fallan con error de conexión (no hay nadie del otro lado para contestar un código HTTP), aunque los servicios están perfectos. Volver a prenderlo y agregar la instancia pasiva: queda punteada, en espera, sin recibir pedidos; todo el tráfico sigue yendo a la activa. Apagar la activa: la pasiva pasa a activa y atiende todo sin un solo error de conexión. Al volver a prender la primera, retoma el rol de activa. Contar que el traspaso en la vida real suele hacerse con una IP compartida que se mueve de una máquina a otra (por ejemplo keepalived) o cambiando el DNS. La pasiva no aporta capacidad mientras espera: es el precio de la disponibilidad. Remarcar el último punto: el proxy decide a dónde va cada pedido, no qué hace el negocio. Si empieza a tener reglas de negocio, se vuelve un monolito escondido. Pregunta para la clase: ¿qué otra pieza que vimos en la clase de load balancing tenía el mismo problema?

API gateway: un proxy reverso para APIs

NavegadorApp móvilsin tokenrespuesta401429404

Todo API gateway es un proxy reverso; no todo proxy reverso es un API gateway. Suma lo que importa con clientes de una API.

App móvil: se porta bien, 1 pedido/s y casi siempre con token.

Inunda: 10 pedidos/s, el doble del límite → 429.

Sin token: pega a la API sin autenticarse → 401.

Escanea: prueba /admin, /.env… rutas que no existen → 404 en la puerta.

  • Agregación: un pedido del cliente → varios servicios → una sola respuesta (espera al más lento).
  • BFF (backend for frontend): un gateway por tipo de cliente, web y móvil.
Cada cliente tiene su color; los puntos huecos son pedidos sin token. Las respuestas vuelven en verde a quien pidió. Prender la autenticación: los huecos rebotan en el gateway con 401 (rojo) y vuelven a su cliente, sin llegar a ningún servicio. Prender el límite: cada cliente muestra cuántos pedidos hizo en el último segundo contra el límite (x/5). Elegir "Inunda": la App móvil pasa a 10 por segundo, su caja se pone naranja y solo a ella le vuelven 429 (naranja); el navegador sigue normal. El límite es por cliente, no global. "Sin token": todos sus pedidos van huecos; con la autenticación prendida rebotan con 401. "Escanea": prueba rutas como /admin o /.env que ninguna regla conoce, y el gateway las corta con 404 (violeta) sin molestar a ningún servicio. Cada abuso lo frena una defensa distinta: límite, autenticación, reglas de ruteo. Mencionar agregación y BFF como funciones típicas de gateway que un proxy genérico no tiene. Resumen

LB, proxy reverso y API gateway

⚖️ Load balancer

  • Elige entre: copias iguales.
  • Por: carga.
  • Además: health checks.

🔀 Proxy reverso

  • Elige entre: servicios distintos.
  • Por: ruta (path, host, header).
  • Además: TLS, caché, compresión, ocultar el backend.

🔑 API gateway

  • Elige entre: servicios distintos.
  • Por: ruta + quién es el cliente.
  • Además: autenticación, límites por cliente, agregación, métricas de uso.

En la práctica: Nginx · HAProxy · Envoy · Traefik · Caddy — gateways: Kong · AWS API Gateway · Azure API Management · Apigee

Cerrar con la progresión: el LB reparte carga entre iguales; el proxy reverso decide por ruta entre servicios distintos; el API gateway es un proxy reverso que además sabe quién es el cliente. En la práctica se combinan y el mismo producto puede cumplir varios roles (Nginx o Envoy hacen de LB, de proxy y, con plugins, de gateway).
